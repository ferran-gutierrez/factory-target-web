- **REQ-1** When localStorage holds a parseable JSON array that mixes valid task objects with invalid entries (for example `{ "id": "keep-1", "title": "Keep me", "completed": false }` followed by `{ "title": "missing id" }`), loading tasks returns only the valid entries with missing `priority` normalized to **normal**.
  `[@test] ../tests/taskPersistence.test.ts`

- **REQ-2** When the app mounts with such partially invalid stored data, the visible task list includes every loaded valid task title (for example **Keep me**) and excludes titles from invalid entries.
  `[@test] ../tests/taskPersistence.test.ts`

- **REQ-3** When the stored value is a parseable JSON array and at least one array entry is invalid, the app shows a visible notice that includes the number of invalid entries that were skipped (for example one skipped when the array has one valid and one invalid object).
  `[@test] ../tests/taskPersistence.test.ts`

- **REQ-4** When localStorage is missing, the stored string is not valid JSON, or the parsed JSON root is not an array, loading yields an empty task list and the skip notice from REQ-3 is not shown after mount.
  `[@test] ../tests/taskPersistence.test.ts`

- **REQ-5** After startup load drops invalid stored entries, localStorage is overwritten to contain only the valid loaded tasks so a subsequent full page reload still shows those tasks and does not retain invalid objects in the stored JSON.
  `[@test] ../tests/taskPersistence.test.ts`

- **REQ-6** When the user selects an import file whose contents are not valid JSON (for example `{ "tasks": [` without closing syntax), the task list titles and order stay unchanged from immediately before the attempt and a visible import error message is shown.
  `[@test] ../tests/taskImportExport.test.ts`

- **REQ-7** An end-to-end journey adds at least two tasks with distinct titles and mixed completion, priority, and due-date fields, exports and captures the JSON file, clears persisted tasks and reloads to an empty list, imports via **Import tasks** with confirmation, asserts on screen for each imported task its title, completion checkbox state, priority label (**Low**, **Normal**, or **High**), and due-date label/value (including no due-date label when unset), then reloads the page and repeats the same per-task title, completion, priority, and due-date assertions.
  `[@test] ../e2e/tasks.spec.ts`

## Assumptions

- Invalid stored array entries use the same field and type rules as import validation (`id`, `title`, `completed` required with correct types; optional `dueDate` string; optional `priority` one of `low`, `normal`, `high`); objects missing only `priority` remain valid and normalize to **normal**.
- A parseable JSON array where every entry is invalid yields an empty task list and a skip notice whose count equals the number of array entries; REQ-3 does not apply when the stored value is completely unreadable per REQ-4.
- The skip notice is a visible, non-error status message in the app shell (for example an element with `role="status"`) that includes the skipped count as digits; it is shown on initial mount after partial recovery and is not used for import failures.
- Partial recovery persists the valid subset to localStorage during the same startup load that drops invalid entries, before the user adds or edits tasks.
- Malformed JSON on import shows the existing parse-failure import error copy and does not open the replace-list confirmation dialog.
- Export, import validation, filters, sort, and other task behaviour from earlier specs stay unchanged except where this spec and updated earlier specs describe load recovery and the export-import E2E assertions.

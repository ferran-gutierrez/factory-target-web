- **REQ-1** The app exposes a search input above the task list (`<ul>`) with an accessible name **Search tasks** so users and tests can locate the control without relying on placeholder text alone.
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-2** Pure search helpers return only tasks whose title contains the query as a case-insensitive substring (for example query `EGG` matches title `Buy eggs` but not `Buy milk`).
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-3** An empty or whitespace-only search query does not hide tasks by title; visibility is determined only by the active all/active/done filter (and sort order) as in earlier specs.
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-4** When the search query is non-empty after trimming, a task is visible only if it passes the active status filter and its title matches the trimmed query per REQ-2 (for example with tasks `Alpha` (active), `Beta` (done), and `Gamma` (active), filter **Active** plus query `a` shows `Alpha` and `Gamma` but not `Beta`).
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-5** When at least one task is stored but the combined status filter and non-empty trimmed search leave zero matching tasks, the app shows a visible **No tasks match** message, hides task rows, and does not show the add-a-task empty-state copy used when there are zero stored tasks.
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-6** When there are zero stored tasks, the app shows the existing add-a-task empty-state message (for example matching `/add a task/i`) and not **No tasks match**, even if the search box contains text.
  `[@test] ../tests/taskFilters.test.ts`

- **REQ-7** Clearing the search input (empty value) immediately restores the task list for the current status filter without a full page reload.
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-8** The search query is not written to localStorage; after a full page reload the search input is empty and every stored task visible under filter **All** appears in the list regardless of what was typed before reload.
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-9** Sort mode (creation order, due date, or priority) applies to the status- and search-filtered subset before rendering list rows.
  `[@test] ../tests/taskSearch.test.ts`

- **REQ-10** An end-to-end journey adds tasks `Cherry task` and `Apple task`, types `apple` into **Search tasks** and verifies only `Apple task` appears, clears search and verifies both titles appear under filter **All**, marks `Apple task` complete, sets filter **Active** with query `apple` and verifies **No tasks match**, switches filter **Done** with the same query and verifies `Apple task` is shown, then reloads the page and verifies the search box is empty and both tasks appear under **All**.
  `[@test] ../e2e/tasks.spec.ts`

## Assumptions

- Search runs on the trimmed query; whitespace-only input is treated as no search per REQ-3.
- **No tasks match** is shown as visible text (for example in a dedicated paragraph) when REQ-5 applies; the task `<ul>` has no `<li>` rows in that state.
- The search input sits in the app shell directly above the task list and below the existing filter and sort controls.
- Status filter still defaults to **all** on reload; neither filter tab nor search text persists—only task records in localStorage.
- Search matches task titles only (not priority labels, due dates, or ids); edit mode row titles count once saved back to the list.
- Export and import continue to operate on the full stored task array regardless of search visibility.

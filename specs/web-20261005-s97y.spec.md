- **REQ-1** The add-task form exposes its optional due date input with a visible accessible label whose name is **Due date**, associated with the date control so tests can locate the field by that label without selecting `input[type="date"]` alone.
  `[@test] ../tests/taskDueDateLabels.test.ts`

- **REQ-2** While editing a task, the due date input exposes a visible accessible label whose name is **Edit due date**, associated with the date control so tests can locate the field by that label within the task row.
  `[@test] ../tests/taskDueDateLabels.test.ts`

- **REQ-3** An end-to-end journey adds two tasks with due dates in creation order that is not ascending by due date (first task titled with the later due date `2099-06-01`, second titled with the earlier due date `2000-01-15`), locates the add-form due date field by the **Due date** label, switches sort to **Due date** and verifies list titles appear with the `2000-01-15` task before the `2099-06-01` task, switches sort to **Creation order** and verifies the `2099-06-01` task title appears before the `2000-01-15` task title, edits a task due date using **Edit due date** and verifies the list shows the new due date, and clears a task due date and verifies that row no longer shows an accessible due date for the task.
  `[@test] ../e2e/tasks.spec.ts`

## Assumptions

- Label text is exactly **Due date** on the add form and **Edit due date** in the edit row, matching the existing **Task title** / **Edit task title** naming pattern.
- Association uses a native `<label htmlFor="…">` paired with a stable `id` on the date input, or an equivalent pattern that exposes the same accessible names to Playwright and jsdom.
- The E2E journey may add further tasks or steps (for example overdue checks or reload) as long as REQ-3’s ordering, sort toggling, edit, and clear assertions remain; other due-date behaviour stays governed by `web-20261004-cbd7.spec.md`.
- Supersedes web-20261004-cbd7 REQ-14: the due-date E2E journey centered on overdue marking, due-date sort, and persistence after reload becomes a journey that proves sort order when tasks are added out of due-date order, toggles back to creation order, and covers edit and clear due date via labeled controls (persistence after reload remains required by web-20261004-cbd7 REQ-11 and its tests).
- Unit tests for REQ-1–REQ-2 run in jsdom via `mountTaskApp`, consistent with existing store UI tests.

  `[@test] ../e2e/tasks.spec.ts`

## Assumptions

- Priority is one of the string values `low`, `normal`, or `high` on each task; the UI shows the capitalized labels **Low**, **Normal**, and **High**.
- The add-form control is a `<select>` (or equivalent) defaulting to **Normal**; the edit-row control uses the same three options with accessible name **Edit priority**, matching the **Due date** / **Edit due date** label pattern.
- High-priority highlighting applies on the list row (`<li>`) via a stable test hook such as `data-priority="high"` or a `priority-high` class; only high priority receives that highlight.
- Priority sort applies to the current status- and search-filtered subset, consistent with creation-order and due-date sort; sort mode still defaults to **Creation order** on full page reload and is not persisted in localStorage.
- When persisting new tasks, the priority field is stored explicitly (including `normal`); legacy records without the field normalize to `normal` on load; invalid entries in the same stored array are dropped and counted in the load skip notice per robust load behaviour.
- Existing due-date, filter, edit, delete, and overdue behaviour from earlier specs remains unchanged; this task adds priority fields and sort only within the allowed paths and bundle budget.
